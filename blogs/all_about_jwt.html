1. Introduction

  • JWT are cryptographically signed token from an authorization server

  • They are stateless and are used to validate if the request is coming from a genuine authenticated user, without asking AUTH server or accessing any database

  • JWT are payloads which are

    • Encoded (Base64 URL) encoded

    • They contain a signature that authenticates their validity (not tampered with)

1.1. What happened before JWT

  • User creates a user profile

  • The auth server generates a token that is stored in the database

  • Once the token is passed to sub services, they need auth server to validate the token (which also means a database hit)

  • The design requires a lot to scale and also a great dependency on auth server and the database

1.2. What changes JWT bought in

  • Since JWT tokens are stateless, sub services do not have to call auth server to validate

2. Components of JWT

  • Header

    • Information (metadata) about token

    • Algorithm used for generating the signature

    • type(JWT)

  • Payload

    • Claims data

      • issuer

      • sub (userID)

      • audience

      • expiry (and others)

    • Is encoded and not encrypted

  • Signature

    • Tamper check

3. How an AUTH server generates JWT

  • Validate credentials (database call)

  • Fetch claims (this becomes payload)

    • What user is allowed to do ?

    • Other info

    • Expiry timestamp

  • Generate header

    • Choose the algo used for generation of signature

      • HS-256

      • RS-256

  • Generate signature

    • Chooses the algo (HS/RS-256)

    • Use Header + Payload to generate signature using algo

  • Generate final token body and return

    • The payload is encoded (Base64 URL) not encrypted

3.1. Difference between HS/RS-256 signature generation algo

  • HMAS + SHA-256 (HS256)

    • Symmetric cryptography

    • One key used as both private and public

      • Create the signature (private == Key1)

      • Validate the signature (public == Key2)

    • Contains risk since if one engine leaks key the signature can be forged

  • RSA + SHA-256 (RS256)

    • Symmetric cryptography

    • Two keys used

      • Private → Generate signature

      • Public → Decrypt signature

        • Remain sames for all the consumers

    • Lesser risk

      • Even if public key is leaked new signature cannot be forged

4. How sub systems authenticate

  • Decode the payload

  • Verify the algo type (should match)

  • Verify(header+payload, publickey, signature)

4.1. Additional checks

  • Correct expiry timestamp

  • Issuer

  • Token for the service (AUD)

5. Key Rotation

5.1. Why rotate

  • Cryptographic keys weaken over time — longer a key lives, more tokens signed with it, bigger the blast radius if leaked

  • Compliance frameworks (SOC2, PCI-DSS) mandate periodic rotation

  • If private key leaks, attacker can forge JWTs for every user until key is revoked

  • Rotation limits damage window and forces attackers to re-compromise

5.2. The core problem

  • JWTs are stateless — issued tokens live until exp

  • If you swap keys instantly, every in-flight token signed with old key breaks → mass logout

  • Need overlap window: old key valid for verification, new key used for signing

5.3. The kid (Key ID) header

  • Each signing key is tagged with unique kid string (e.g. "2026-07-key-01")

  • Auth server includes kid in JWT header when signing:

{
  "alg": "RS256",
  "typ": "JWT",
  "kid": "2026-07-key-01"
}

  • Sub-service reads kid before verifying, looks up matching public key from JWKS

5.4. JWKS endpoint

  • Standard URL: https://auth.example.com/.well-known/jwks.json

  • Returns JSON array of active public keys:

{
  "keys": [
    {
      "kid": "2026-07-key-01",
      "kty": "RSA",
      "alg": "RS256",
      "use": "sig",
      "n": "0vx7agoebGcQSuu...",
      "e": "AQAB"
    },
    {
      "kid": "2026-04-key-01",
      "kty": "RSA",
      "alg": "RS256",
      "use": "sig",
      "n": "xGOr-H7A-Rr8-Xy...",
      "e": "AQAB"
    }
  ]
}

  • Sub-services fetch JWKS on startup, cache it, refresh every N minutes

5.5. Rotation flow (step by step)

  1. T0 — Generate new RSA keypair. Assign new kid (e.g. 2026-08-key-01)

  2. T0 — Add new public key to JWKS endpoint alongside old key. Now JWKS returns both keys

  3. T0 + cache_ttl — Wait for all sub-services to refresh JWKS cache and pick up new key. Critical — if you sign with new key before services see it, verification fails

  4. T1 — Auth server switches signing to new private key. New tokens carry new kid. Old tokens still verify against old public key

  5. T1 + max_token_lifetime — All tokens signed with old key have expired. Safe to retire old public key from JWKS

  6. T2 — Remove old key from JWKS. Delete old private key from KMS

5.6. Verification logic on sub-service

def verify_jwt(token: str) -> dict:
    header = decode_header(token)
    kid = header["kid"]
    alg = header["alg"]

    if alg not in ALLOWED_ALGS:  # Pin allowed algorithms
        raise InvalidToken("bad alg")

    public_key = jwks_cache.get(kid)
    if public_key is None:
        jwks_cache.refresh()  # Force refresh on unknown kid
        public_key = jwks_cache.get(kid)
        if public_key is None:
            raise InvalidToken("unknown kid")

    return jwt.decode(token, public_key, algorithms=[alg])

5.7. Best practices

  • Rotate on schedule — every 30–90 days for signing keys

  • Rotate immediately on suspected compromise — do not wait for scheduled rotation

  • JWKS cache TTL — keep short (5–15 min) so new keys propagate fast

  • Never reuse kid — always mint new identifier per key

  • Reject unknown kid — after one JWKS refresh, if kid still not found → fail closed

  • Store private keys in KMS/HSM — never in env vars, config files, or Git

  • Pin alg allowlist — prevent alg: none and RS256→HS256 confusion attacks

  • Log key usage — track which kid signs how many tokens to catch anomalies

  • Automate rotation — manual rotation gets skipped. Use cron/scheduler

6. When NOT to use JWT

JWT is a solid tool for stateless, distributed auth — but it is not a universal replacement for sessions. Use the wrong tool and you inherit problems that opaque sessions solved decades ago.

6.1. Use opaque session tokens instead when…​

  • You need instant revocation — logout, password change, account ban must take effect immediately. Stateless JWTs cannot be revoked mid-life without adding a database lookup (which defeats the point of JWT)

  • You control both client and server — monolith or single backend. Session ID in a cookie + Redis lookup is simpler, smaller, and revocable

  • Payload contains sensitive data — JWTs are Base64-encoded, not encrypted. Anyone with the token reads the claims. Use JWE (encrypted JWT) or keep sensitive data server-side

  • User data changes frequently — roles, permissions, plan tier baked into token stay stale until expiry. Session lookup always reads current state

  • Small scale / low traffic — the "no database hit" benefit does not matter. Complexity cost is not worth it

  • Regulated environments — some compliance frameworks require session termination on demand, which stateless JWT cannot guarantee

6.2. Use JWT when…​

  • Distributed microservices need to verify auth without hitting central auth server

  • Cross-domain SSO (OIDC ID tokens)

  • Third-party API access (short-lived access tokens)

  • Machine-to-machine auth where revocation is not critical

7. Challenges and Pitfalls

7.1. Revocation is hard

  • Once issued, JWT is valid until exp — server has no way to invalidate

  • Mitigations:

    • Short access token TTL (5–15 min) + refresh tokens

    • Maintain a blocklist (Redis) of revoked jti values — but this adds statefulness

    • Token versioning — store token_version in DB per user, embed in JWT, reject if mismatch on critical routes

7.2. alg: none attack

  • Attacker crafts a token with header {"alg": "none"} and no signature

  • Buggy libraries accept it as valid

  • Fix: server must maintain an allowlist of algorithms and reject anything else

7.3. Algorithm confusion (RS256 → HS256)

  • Server expects RS256 (asymmetric). Attacker changes header to HS256 (symmetric)

  • Attacker signs token using the public key as HMAC secret

  • Server verifies with public key thinking it is HMAC → token accepted

  • Fix: pin exact algorithm server-side. Never let JWT header dictate verification algo

7.4. Storing JWT on the client — no good option

Storage Vulnerability

localStorage

XSS — any injected script reads token

sessionStorage

XSS — same problem, worse lifecycle

Cookie (non-httpOnly)

XSS

Cookie (httpOnly + Secure + SameSite)

CSRF — mitigated with SameSite=Strict/Lax + CSRF tokens

In-memory (JS variable)

Lost on refresh, needs silent refresh flow

  • Least-bad: httpOnly + Secure + SameSite=Strict cookie for web apps

7.5. Token size bloat

  • JWT includes header + payload + signature, all Base64-encoded

  • Typical JWT: 500 bytes – 2 KB

  • Sent on every request → bandwidth cost adds up

  • Some proxies/load balancers cap header size (8 KB default in nginx) — big JWTs get rejected

  • Fix: keep claims minimal. Do not stuff full user profile into token

7.6. Clock skew across services

  • exp and nbf checked against local clock

  • If auth server and sub-service clocks drift, valid tokens get rejected or expired tokens accepted

  • Fix: run NTP everywhere. Allow small leeway (30–60s) in verification

7.7. Trusting the header before verifying

# BAD — trusts attacker-controlled header
header = decode_header(token)
key = fetch_key(header["kid"])
jwt.decode(token, key, algorithms=[header["alg"]])  # attacker picks algo

  • Verify signature first, then trust claims

  • Pin algo from server config, not from token header

7.8. Refresh token theft

  • Refresh tokens live longer (days/weeks) → juicier target

  • If stolen, attacker gets fresh access tokens indefinitely

  • Mitigations:

    • Refresh token rotation — issue new refresh token on every use, invalidate old one

    • Reuse detection — if same refresh token used twice, revoke entire token family (probable theft)

    • Bind refresh token to device fingerprint / IP

7.9. Sensitive data in payload

  • Payload is encoded, not encrypted

  • Anyone with the token (client, proxies, logs) can decode and read claims

  • Do not put PII, passwords, internal IDs, or secrets in JWT

  • If encryption needed → use JWE (JSON Web Encryption)

7.10. Overlong expiry

  • "1 year expiry so users do not log out" → if token leaks, attacker has 1 year of access

  • Access tokens: minutes, not days

  • Long-lived sessions belong in refresh tokens (revocable) or session cookies

7.11. Missing standard claim validation

  • Sub-services often verify signature but skip claim checks

  • Always validate:

    • exp — not expired

    • nbf — not used before valid time

    • iss — issued by expected auth server

    • aud — token intended for this service

    • iat — sanity check issue time

7.12. JWT is not a session

  • JWT proves identity at a point in time. Sessions imply ongoing state

  • Do not use JWT to store shopping cart, form state, UI preferences

  • Keep JWT small and auth-focused. Push session state to server-side store
